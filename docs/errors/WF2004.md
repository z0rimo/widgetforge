# WF2004: Widget receiver with intent-filter lacks android:exported

**Symptom:** The build fails during manifest merging. The error names the `<receiver>` element and says that `android:exported` has to be given an explicit value because the component declares an intent filter. (Reproduced with Flutter 3.32.0 / AGP 8.7.3 and `targetSdk = 31`; the exact wording comes from the build tool and is not reproduced here.)

**Cause:** Apps that target Android 12 (API 31) or higher must declare `android:exported` explicitly on activities, services and broadcast receivers that have an `<intent-filter>` (see the Android 12 behavior changes page, section on safer component exporting; it applies to apps that target Android 12 or higher).

**Detection:**
- A `<receiver>` that has an `<intent-filter>` and no `android:exported`, judged **on its own manifest**. A receiver in `src/main` is judged alone; a receiver that exists only in another source set (debug, release, a flavor) is judged in that manifest. Declarations are never summed across source sets: a main-manifest receiver without the attribute is reported even if the debug manifest adds it, because a variant without that override (for example release) still fails (observed: such a project built in debug and was rejected without the override).
- `targetSdk` is read from `android/app/build.gradle(.kts)` when it is a plain integer. With a number below 31 nothing is reported and a note says so (observed: a debug build with `targetSdk = 30` and no `android:exported` succeeded). When the value is not a plain integer (for example `flutter.targetSdkVersion`), the rule assumes API 31 or higher. Flavor-specific `targetSdk` values are not read.
- Practical note (observed): a release build with `targetSdk = 30` failed on the unrelated lint check `ExpiredTargetSdkVersion`, so very low targets rarely reach release.

**Fix:** Add `android:exported="true"` to the widget `<receiver>`.
